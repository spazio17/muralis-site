Remote control

How to control a Muralis panel from a distance: over HTTP, over MQTT, or from Home Assistant. Each command has a short description, its arguments, an example and the real reply. The examples use 192.0.2.42 for the panel and 192.0.2.10 for the MQTT broker; put your own addresses in their place.

Before you start

Reload the page, over HTTP

curl -k -u :your-admin-password -X POST https://192.0.2.42:8080/api/command -d cmnd=kiosk.reload

The same over MQTT

mosquitto_pub -h 192.0.2.10 -t kiosk/hallway-panel/command -m kiosk.reload

Reply

{"status":"accepted","detail":""}
  • Free. The web admin, the HTTP API and MQTT work on every panel.
  • The web admin starts once an admin password of at least 8 characters is stored and its switch is on. Port 8080 until changed; any port from 1024 to 65535.
  • MQTT starts as soon as a broker host is stored. A username and a password are optional.
  • One command set. HTTP and MQTT run the same code, so a command behaves and is refused in the same words on both. After an accepted command the panel republishes its MQTT state within half a second.
  • Device owner. Three things need the device-owner install (by QR at setup, or dpm set-device-owner over adb): system.reboot, the real screen-off, and CPU and temperature readings on stock Android.
More about MQTT over TLS

The connection is plain TCP unless Encrypted (TLS) is on. With TLS the broker is trusted when Android trusts its certificate for its name, or when its certificate is the one trusted on the panel: after the first refused connection both surfaces show its SHA-256 and a Trust button. A client certificate uploaded in the web admin (a PEM certificate and an unencrypted key, with clientAuth) is presented when the broker asks for one. Without TLS, use MQTT on a network you trust.

HTTP

HTTPS and the certificate

The panel serves HTTPS with a certificate it made itself, so a browser warns once; one click accepts it. A plain http:// request on the same port gets a redirect to the https address and is never asked for a password.

curl -i http://192.0.2.42:8080/api/stats

Reply

HTTP/1.1 301 Moved Permanently
Location: https://192.0.2.42:8080/

This panel speaks HTTPS: https://192.0.2.42:8080/

In the examples -k tells curl to accept the panel’s own certificate. To check it, compare the fingerprint the browser shows with the one on the panel’s web-admin card, on the web admin page, and in config.http_certificate_sha256. To pin it, save it once with openssl s_client -connect 192.0.2.42:8080 -showcerts and pass it to curl with --cacert.

A certificate of your own. Upload a certificate and its key, for example from Let’s Encrypt, and the panel serves it instead. Send the same request again after each renewal.

curl -k --proto =https -u :your-admin-password https://192.0.2.42:8080/api/certificate \
     -F certificate=@fullchain.pem -F key=@privkey.pem

Reply

{"status":"accepted","detail":"saved"}
More about your own certificate

The certificate file holds one or more PEM blocks, the server’s certificate first, then any intermediates (fullchain.pem as certbot writes it, or cert.pem and chain.pem pasted together); a root in it is left out. The key is an unencrypted PEM key, RSA or EC (BEGIN PRIVATE KEY, BEGIN EC PRIVATE KEY or BEGIN RSA PRIVATE KEY). One file holding both also works. Nothing is kept until the key is shown to belong to the first certificate.

An upload must come over HTTPS: pass --proto =https so curl never sends the key over plain HTTP. A browser shows no warning when it trusts the authority and the address you open is a name or address in the certificate.

Choose between your certificate and the panel’s own on the panel’s web-admin card or with the instant setting http_certificate; an upload chooses itself. An upload that cannot be read when the panel starts is not served: the panel’s own certificate is, and both surfaces say why, as does config.http_certificate_problem.

Refused with:

  • no certificate was chosen
  • the request was not a file upload
  • the upload did not arrive complete; please try again
  • this page is served over plain HTTP right now, and a private key must not cross the network unencrypted
  • no certificate was found; a certificate file begins with -----BEGIN CERTIFICATE-----
  • that is a certificate request; upload the certificate the authority sent back for it
  • no private key was found; a key file begins with -----BEGIN PRIVATE KEY-----
  • more than one private key was given
  • the private key is protected by a passphrase, and a panel has nowhere to type one when it starts; save it without one with openssl pkey -in key.pem -out key-open.pem
  • the private key does not belong to the certificate
  • the private key belongs to another certificate in the file; the server's own certificate has to come first
  • the certificate's key is …; the web admin serves RSA and EC keys
  • the certificate is not one for a server (its extended key usage has no serverAuth), and no browser accepts it for one
  • the certificate's key usage has no digitalSignature, and no browser accepts it for a server
  • a name in the certificate is longer than 253 characters, which no browser matches to an address
  • more than 8 certificates were given
  • a certificate in the file cannot be read
  • the private key cannot be read
  • this panel could not keep it; try again
  • this panel could not keep it, and the one it had stays; try again
  • this panel could not keep it; upload it again

Authentication

HTTP Basic on every request, the web admin page included. The username is ignored; only the password counts. There are no cookies, tokens or sessions.

curl -k -i https://192.0.2.42:8080/api/stats

Reply

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Muralis"
Content-Type: text/plain

Unauthorized

Five wrong passwords from one address lock that address out: 429 Too Many Requests with a Retry-After header. The lockout lasts 30 seconds the first time, doubles each time up to 15 minutes, and is forgotten after an hour of quiet. The status document counts lockouts in runtime.auth_lockouts, with the address.

From a browser

Every POST is checked against cross-site requests. A request with Sec-Fetch-Site must say same-origin or none; a request with Origin must match the Host it went to. A request with neither header, as curl and automations send, passes.

curl -k -u :your-admin-password -H 'Origin: http://evil.example' -X POST https://192.0.2.42:8080/api/command -d cmnd=kiosk.reload

Reply, HTTP 403

Forbidden: Origin does not match Host

Fleet alerts

Alerts are the sixth section a fleet can share (the alert_* settings). While the section is shared with a panel, the panel judges itself once a minute: the page failed to load, the battery is below the threshold, the processor temperature is above it, a combination was used, five wrong PINs locked the escape. One panel of the fleet, the online one whose id sorts first, also judges which panels are offline, not heard from for alert_offline_minutes. Each alert is said once: on when the condition starts, off when it ends, never repeated while unchanged; a combination used is on only, once per use. It goes to all three destinations that are set: a notification on the raising panel (cleared on off), a publish on alert_mqtt_topic on the panel’s own broker (not retained, not Home Assistant discovery), and a POST of the same JSON to alert_webhook_url, with an eight-second deadline and no retry. Outside a fleet, or with the section unshared, nothing is raised.

{"fleet":"Home","panel":"Kitchen","panel_id":"kiosk-1a2b3c4d","kind":"battery","state":"on","detail":"12%","at":"2026-10-13T10:00:00Z"}

kind is one of offline, page_error, battery, temperature, combination_used, pin_lockout; detail is a short word of the condition (the page’s error, the percentage, the degrees, how long a panel was not heard from) and may be empty.

Between panels

The panels of a fleet talk to each other on the member port (fleet_port, 8081 until changed), not on the web admin’s: mutual TLS, where a caller is admitted by its fleet key alone and the password plays no part. Two of those routes carry what the Fleet page shows; the rest (joining, the fleet’s list, the heartbeat) are the fleet’s own business and not an interface.

Commands

Sending one

Over HTTP, always a POST to /api/command, with the command in cmnd and its arguments as form fields, in the query string, or as JSON. Over MQTT, publish on kiosk/<id>/command: a bare command name, or a JSON envelope with the arguments.

HTTP, form fields

curl -k -u :your-admin-password -X POST https://192.0.2.42:8080/api/command \
     -d cmnd=display.brightness -d percent=40

HTTP, JSON

curl -k -u :your-admin-password -X POST https://192.0.2.42:8080/api/command \
     -H 'Content-Type: application/json' \
     -d '{"command":"display.brightness","args":{"percent":40}}'

MQTT, JSON envelope

mosquitto_pub -h 192.0.2.10 -t kiosk/hallway-panel/command \
     -m '{"id":"evening-1","command":"display.brightness","args":{"percent":40}}'

MQTT result, on kiosk/hallway-panel/command/result

{"id":"evening-1","status":"accepted","detail":"","timestamp_ms":1788948057237}

The arguments are url, percent, value, enabled and beacon; a few commands take more, named in their tables. enabled takes true/false, 1/0 or on/off. Over MQTT the result carries the same status and detail as the HTTP reply, plus your id (up to 96 characters) and timestamp_ms.

Replies

statusMeaningHTTP code
acceptedDone, or handed to the screen. detail is usually empty.200
rejectedA bad argument, or something the panel cannot do now. detail says why, in one sentence.200 when the command was understood; 400 when the request itself was broken (missing command, malformed json, enabled must be true or false)
unsupportedAn unknown command, or system.reboot without device owner.200

Read status, not the HTTP code. A command that was understood and refused is still HTTP 200.

Pop-ups and cameras

Network cameras are set on the Cameras page of the panel or the web admin (or with POST /cameras): each has a name, an address and an optional sign-in. Groups put cameras together under a name of their own.

More about cameras

A camera has a name (1 to 40 characters, unique, not Web page, which means the web page in the camera view), an address (a snapshot, an MJPEG stream or a camera page, http:// or https://), an optional full-screen address (the same camera’s bigger stream, used when it is shown alone), and an optional user and password. At most 10 cameras.

A group has a name of its own and shows its cameras as one grid, laid out by their number and the screen’s shape. At most 10 groups; a camera may be in several; no group and no camera share a name.

The sign-in is stored as a secret and sent, Basic or Digest as the camera asks, to that camera’s host only. A sign-in typed into the address, before the host (http://user:pass@host/) or in the query (&user=…&password=…, also usr and pwd), is taken out and stored the same way; in the query it becomes {user} and {password}, filled in only when the panel fetches the camera. A password with no user is refused: a camera that ignores the user takes any name. A refused sign-in is tried once a fetch, never again at once, so a wrong password does not lock the panel out.

Fetching. A camera is only streamed: what it sends is drawn from memory and never written to the panel. An https:// camera needs a certificate Android trusts, or one trusted on the panel like a page’s; until then it waits in the status document. A camera that cannot be shown says why in its place: No picture, Sign-in refused or Certificate not trusted.

MQTT

<id> below is the panel’s device id, hallway-panel in the examples. Two panels on one broker need two different ids.

Connection

TransportMQTT 3.1.1 over plain TCP (default port 1883), or over TLS when Encrypted (TLS) is on (brokers usually listen on 8883). Clean session, keepalive 30 s.
Client idThe device id.
Last willkiosk/<id>/availability = offline, retained.
On connectPublishes online, subscribes to its command topic, to homeassistant/status and to its own homeassistant/device/<id>/config, whose retained copy says what it announced before, then publishes discovery. It waits up to five seconds for that copy, so a broker with access lists must let the panel read its own discovery topic as well as write it. When Home Assistant announces itself as back online, discovery is published again.
ReconnectAutomatic after a lost connection. A broker that was unreachable when the panel started is retried when the MQTT settings are saved or at the nightly restart.

Home Assistant discovery

One retained bundle on homeassistant/device/<id>/config creates the whole device, named Muralis <id>. Every entity reads the state topic and sends to the command topic, so nothing has to be written in YAML.

More about which entities are announced

The manufacturer and model come from the hardware, the software version from the app. An entity the panel cannot serve is not announced at all: no battery sensors without a battery, no automatic brightness without a light sensor, no auto orientation without an accelerometer, no reboot button and no sleep option without the device-owner install.

An entity the panel announced and then stops announcing (a sensor switched off, a deleted rule) is removed from Home Assistant. The panel removes only what it announced itself, so a new panel sends no removal at all. A removal Home Assistant misses because it is offline at that moment leaves the entity unavailable until you delete it, as with other MQTT devices.

Liveness

A separate entity, MQTT state, is a connectivity sensor on the availability topic with a 90 second expiry. The panel says online every 30 seconds; 90 seconds of silence turn the sensor off, even if a broker restart brought back a stale retained online. A panel that goes quiet reads unavailable in Home Assistant, never a stale online.
